# Руководство по обучению системы технического зрения ALKU

**Проект:** SW001-ALKU  
**Модель:** Ultralytics YOLO11 (detect или pose)  
**Назначение:** сбор данных, калибровка камеры, разметка, обучение, проверка и ввод модели в `cv-service`.

---

## Как пользоваться руководством

Документ описывает не учебный пример «YOLO в вакууме», а фактический путь данных в проекте:

```text
Hikvision camera
    -> camera-service
    -> Redis: camera_frame
    -> cv-service
       undistort -> ArUco perspective transform -> YOLO11
       -> postprocessor -> Redis: processed_frame
    -> master-service получает результаты CV
    -> робот принимает производственное решение
```

Для каждого нового изделия или варианта дефекта рекомендуется проходить главы последовательно. Пропуск калибровки или валидации может дать модель с хорошими метриками на компьютере, но неправильными координатами для робота.

Команды приведены для PowerShell и запускаются из корня репозитория, если не указано иное. Перед работой следует сделать резервную копию `data/config.json`, готовых моделей и существующих датасетов.

> Важное замечание о текущем репозитории: файл `yolo-trainer/trainer.py` сейчас выбирает базовые веса `yolo26m.pt` и `yolo26m-pose.pt`. Это не YOLO11. Для обучения YOLO11 нужно заменить эти значения на `yolo11m.pt` и `yolo11m-pose.pt` либо запускать отдельную команду Ultralytics, приведённую в главе 9. Наличие файла с именем `yolo11` в каталоге ещё не означает, что он используется.

## 1. Цель системы и границы ответственности сервисов

### 1.1. Что должна выдавать модель

В проекте есть два режима:

- **Detection**: объект описывается bounding box, классом и вероятностью.
- **Pose**: кроме bounding box и класса модель выдаёт keypoints. Они используются postprocessor-ом для вычисления точки захвата, ориентации или производственного признака.

В `data/config.json` эти режимы представлены как `yolo-detect` и `yolo-pose`. Например, `312.229.001` настроен как detection, а `0401.17.02.023` как pose.

Модель не должна обучаться «на всё подряд». Её задача должна быть сформулирована измеримо:

1. какие изделия или дефекты распознаются;
2. какие классы допустимы;
3. нужно ли возвращать координаты захвата;
4. какая минимальная вероятность нужна для запуска операции;
5. что происходит, если объект не найден или найдено несколько кандидатов.

Пример постановки для изделия `312.229.001`:

```text
Вход: откалиброванный кадр рабочей зоны.
Выход: один объект класса product_312_229_001 или defect_312_229_001.
Критерий приемки: IoU >= 0.5, recall рабочего класса >= 0.98,
ошибочный захват на контрольной выборке = 0.
```

### 1.2. `camera-service`

`camera-service/app/main.py` подключается к Hikvision по GigE, применяет экспозицию из `HikCamera.ExposureValue`, получает кадры и записывает последний JPEG в Redis-ключ `camera_frame`. Перед публикацией выполняется коррекция оптической дисторсии по `/data/distortion_coeffs.npz`.

Ключевые параметры:

```json
"HikCamera": {
  "IPAddress": "192.168.7.101",
  "DeviceName": "MV-CH120-20GM",
  "FrameInterval": 0.0,
  "ExposureValue": 4000
}
```

`FrameInterval` задаётся в секундах. Нулевой интервал даёт максимальную частоту цикла и может перегрузить CPU, Redis и сеть. Для сбора датасета лучше фиксировать экспозицию и частоту, чтобы изображения были сопоставимы.

В текущем коде камера публикует только последний кадр: Redis не является архивом датасета. Для сохранения истории используйте `DatasetGrabber`, endpoint `save_frame` или отдельное копирование кадров.

### 1.3. `cv-service`

`cv-service/app/FrameProcessor.py` получает JPEG из `camera_frame` и работает в таком порядке:

1. декодирует JPEG;
2. если матрица ArUco отсутствует, показывает найденные маркеры и не запускает детектор;
3. при наличии калибровки выполняет `warpPerspective` в размер `MarkersXDistance x MarkersYDistance`;
4. вызывает `Detector`;
5. передаёт предсказания в выбранный postprocessor;
6. рисует результат и публикует JPEG в `processed_frame`.

Размеры в `data/config.json` задаются в миллиметрах, а `Calibrator.py` умножает их на 10. При текущих значениях целевой кадр получается примерно `4895 x 2960` пикселей. Это нужно учитывать при выборе `imgsz`, размере объектов и скорости инференса.

`Detector` загружает файл из `/data/models`, порог из `Models.<name>.ConfidenceThreshold` и postprocessor из `/data/postprocessors`. Поэтому файл `.pt`, запись в конфигурации и процессор являются одной поставляемой версией модели.

### 1.4. `master-service`

`master-service/app/main.py` управляет производственным процессом, состояниями сенсоров и командами роботу. Он не обучает и не загружает YOLO. Взаимодействие с результатами компьютерного зрения выполняется фоновой логикой `CVBackground`, а API предоставляет, среди прочего, команды запуска, паузы, остановки, проверки эталона и получения данных.

Практический вывод: изменение модели сначала проверяется в `cv-service`, затем в связке `cv-service` + `master-service`, и только после этого на реальном цикле робота. Нельзя считать модель готовой только потому, что `model.val()` показал высокую метрику.

## 2. Подготовка оборудования и программной среды

### 2.1. Оборудование

Перед сбором данных проверьте:

- камера жёстко закреплена и не меняет положение;
- объектив, защитное стекло и рабочая зона чистые;
- освещение включается одинаково от кадра к кадру;
- изделие лежит в том же диапазоне координат, где будет работать робот;
- кабель GigE и IP-адрес камеры доступны с машины, где работает контейнер;
- GPU NVIDIA виден Docker и имеет достаточную видеопамять;
- на время сбора данных робот переведён в безопасное состояние.

Любое изменение высоты камеры, фокуса, освещения или размеров рабочей зоны после калибровки требует повторной проверки homography. Изменение объектива требует новой оптической калибровки.

### 2.2. Проверка Docker и Redis

Из корня проекта:

```powershell
docker compose config
docker compose ps
docker compose logs --tail=100 camera-service
docker compose logs --tail=100 cv-service
```

Проверка API через nginx:

```powershell
curl http://localhost/api/camera/health
curl http://localhost/api/cv/health
curl http://localhost/api/master/health
```

`camera-service` использует `network_mode: host` и в compose получает `REDIS_HOST=localhost`. `cv-service` и `master-service` находятся в сети `alku-network` и используют Redis как `redis`. Не меняйте эти значения местами без изменения сетевой схемы.

### 2.3. Проверка CUDA

В контейнере CV:

```powershell
docker compose exec cv-service python -c "import torch; print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'CPU')"
```

Если CUDA недоступна, `FrameProcessor` может перейти на CPU для perspective transform, но модель и обучение будут существенно медленнее. Текущий `trainer.py` вызывает `model.to("cuda")` без проверки, поэтому запуск на машине без GPU завершится ошибкой.

## 3. Оптическая калибровка камеры

В проекте есть два разных вида калибровки, и их нельзя смешивать.

### 3.1. Калибровка дисторсии по шахматной доске

Она находит матрицу камеры и коэффициенты искажений объектива. Скрипты находятся в `Calibration/get_images.py` и `Calibration/calibrate.py`.

Текущие параметры:

```python
CHESSBOARD_SIZE = (9, 6)
SQUARE_SIZE = 0.027
```

Скрипт сбора:

```powershell
python Calibration/get_images.py
```

Рекомендуемый порядок:

1. Зафиксировать камеру и выбрать рабочую экспозицию.
2. Разместить шахматную доску ровно, под наклонами и на разных расстояниях.
3. Собрать не менее 15-25 кадров, хотя код требует минимум 5 валидных.
4. Заполнить кадрами разные части изображения: центр, четыре угла, края.
5. Не использовать почти одинаковые кадры.
6. Убедиться, что все 9 x 6 внутренних углов видны и не закрыты бликами.
7. Запустить расчёт:

```powershell
python Calibration/calibrate.py
```

Скрипт проверяет распределение углов по сетке 3 x 3 и минимальное покрытие. Он использует `cv2.calibrateCamera` с фиксированными параметрами `K3`, касательной дисторсии и principal point. Результатом является `Calibration/calibration_chess.npz` с массивами `cameraMatrix` и `distCoeffs`.

### 3.2. Как установить результат в runtime

`camera-service` и `cv-service` ищут файл по имени из `CameraDistortionCoeffsName`, сейчас это `distortion_coeffs.npz`, в каталоге `/data`. Поэтому результат надо привести к имени и расположению, например:

```powershell
Copy-Item Calibration\calibration_chess.npz data\distortion_coeffs.npz
```

Перед копированием убедитесь, что архив содержит именно ключи:

```powershell
python -c "import numpy as np; x=np.load('data/distortion_coeffs.npz'); print(x.files); print(x['cameraMatrix'].shape); print(x['distCoeffs'].shape)"
```

В репозитории также есть готовые файлы в `Calibration`, `DatasetGrabber` и `data`. Всегда фиксируйте, какой набор был получен для текущей камеры. Нельзя подменять файл только по совпадению имени.

### 3.3. Контроль качества

Сделайте undistort на нескольких исходных кадрах и визуально проверьте прямые линии по краям. Для количественного контроля сохраните среднюю ошибку репроекции из вывода `calibrate.py`. После установки файла перезапустите camera-service и проверьте логи:

```powershell
docker compose restart camera-service cv-service
docker compose logs -f camera-service
```

В текущем `camera-service` при отсутствии коэффициентов переменная `undistorted` может остаться неинициализированной перед JPEG-кодированием. Это дефект обработки отказа: для рабочего стенда отсутствие `data/distortion_coeffs.npz` следует считать блокирующей ошибкой, а не продолжать запуск вслепую.

## 4. Геометрическая калибровка рабочей зоны ArUco

### 4.1. Назначение

Оптическая калибровка исправляет объектив. ArUco-калибровка переводит наклонённую плоскость стола в прямоугольную систему координат, в которой обучается и работает YOLO.

`cv-service/app/Aruco.py` использует словарь `DICT_4X4_100`. В конфигурации назначены четыре угловых маркера:

```json
"Markers": {
  "MarkersXDistance": 489.5,
  "MarkersYDistance": 296,
  "Marker00ID": 0,
  "MarkerX0ID": 1,
  "MarkerXYID": 2,
  "Marker0YID": 3
}
```

Маркер 0 соответствует началу, 1 направлению X, 2 дальнейшему углу, 3 направлению Y. Физические расстояния должны быть измерены между теми точками маркеров, которые используются в коде.

### 4.2. Требования к установке

1. Наклейте маркеры на одну плоскость.
2. Не меняйте их положение после калибровки.
3. Используйте правильные ID и словарь `DICT_4X4_100`.
4. Уберите блики и убедитесь, что все четыре маркера видны одновременно.
5. Измерьте `MarkersXDistance` и `MarkersYDistance` в миллиметрах.
6. Проверьте, что область назначения не обрезает места, где реально лежит изделие.

### 4.3. Калибровка через API

После запуска сервисов:

```powershell
curl -X POST http://localhost/api/cv/calibrate
```

При успехе матрица сохраняется в `data/calibration_matrix.npy`. Сброс:

```powershell
curl -X POST http://localhost/api/cv/uncalibrate
```

Если после калибровки в кадре отображаются маркеры, но модель не работает, проверьте наличие `data/calibration_matrix.npy`, размеры результата warp и журнал CV.

В текущем коде ответ endpoint `/calibrate` обращается к `processor.calibrator.Origin` и `Theta`, хотя `Calibrator.py` эти атрибуты не определяет. Поэтому матрица может сохраниться, а HTTP-ответ вернуть ошибку `AttributeError`. Проверять успех следует по файлу матрицы и состоянию кадра, пока endpoint не будет исправлен.

### 4.4. Контроль геометрии

Положите в рабочую зону линейку или лист с известными размерами. После warp расстояние по X и Y должно соответствовать ожидаемому масштабу. Сохраните контрольный кадр с сеткой и четырьмя маркерами. Этот кадр станет эталоном для будущего сравнения после обслуживания камеры.

## 5. Сбор изображений для датасета

### 5.1. Почему собирать нужно в производственном виде

YOLO обучается на распределении изображений, которое увидит в эксплуатации. Датасет должен включать не только красивые центральные кадры, но и:

- разные положения объекта в допустимой рабочей зоне;
- повороты и перекрытия;
- допустимые изменения яркости;
- реальные блики, тени и загрязнения;
- пустую рабочую зону;
- похожие детали и фоновые объекты;
- редкие, но опасные дефекты;
- кадры без объекта и с частично видимым объектом.

Если в runtime сначала выполняется perspective transform, разметку желательно делать на тех же откалиброванных изображениях, которые подаются в модель. Разметка исходного наклонённого кадра, а затем обучение на warped-кадрах создаёт систематическую ошибку координат.

### 5.2. `DatasetGrabber`

Запуск:

```powershell
python DatasetGrabber/DatasetGrabber.py
```

Интерфейс доступен по адресу `http://localhost:5000`. При наличии `DatasetGrabber/distortion_coeffs.npz` и `DatasetGrabber/calibration_matrix.npy` он выполняет undistort и warp в размер `(4895, 2960)`.

Endpoint сохранения ожидает JSON:

```json
{
  "baseName": "312.229.001-1",
  "exposures": [4000, 5000, 6000],
  "lightLevel": "high",
  "auxLight": "on"
}
```

Пример PowerShell:

```powershell
$body = @{
  baseName = "312.229.001-1"
  exposures = @(4000, 5000, 6000)
  lightLevel = "high"
  auxLight = "on"
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://localhost:5000/save_images -ContentType "application/json" -Body $body
```

Файлы появятся в `DatasetGrabber/images/312.229.001-1/`, например:

```text
exp_5000_light_high_aux_on.jpg
```

Имя каталога удобно использовать как серию или вариант изделия. Ведите отдельную таблицу: дата, изделие, экспозиция, освещение, оператор, камера, состояние калибровки и комментарий.

### 5.3. Стратегия количества

Для первого рабочего прототипа ориентируйтесь на 300-800 изображений на класс, а не на фиксированное магическое число. Для редких дефектов важнее разнообразие и полный охват условий, чем дублирование одного и того же кадра. В pose-задачах добавляйте изображения, на которых keypoints находятся в разных положениях.

Не делайте случайные соседние кадры из одной короткой серии одновременно в train и val. Иначе метрика будет завышена: модель увидит почти тот же кадр на обучении.

### 5.4. Разделение данных

Базовое разделение:

```text
train: 70-80%
val:   10-20%
test:  10-20%
```

Разделяйте по сериям съёмки, изделиям и условиям, а не только случайным перемешиванием файлов. Например, вся серия `312.229.001-17` должна попасть целиком только в одну часть. Тест должен моделировать будущую смену, новую партию и немного изменённое освещение.

## 6. Разметка данных

### 6.1. Выбор типа задачи

Выберите `detect`, если достаточно коробки объекта. Выберите `pose`, если downstream-логика нуждается в точках: например, для ориентации детали или вычисления pick point.

Нельзя обучить detection-модель, а затем ожидать keypoints в `YoloData`. Для pose должны совпадать базовый вес, формат YAML, формат label и `ModelType` в конфигурации.

### 6.2. Имена классов

Используйте стабильные ASCII-имена без пробелов:

```text
product_312_229_001
product_312_229_001_ng
background_reference
```

Не меняйте смысл класса между версиями. Если `NG` означает конкретный дефект, это должно быть одинаково определено для разметчиков и postprocessor-а. Добавление нового класса требует повторной проверки всех старых изображений: часть объектов могла быть ошибочно размечена как прежний класс.

### 6.3. Detection-разметка

Структура:

```text
dataset/
  data.yaml
  train/images/
  train/labels/
  val/images/
  val/labels/
  test/images/
  test/labels/
```

Для изображения `frame_0001.jpg` нужен `frame_0001.txt`. Строка YOLO detection:

```text
class_id center_x center_y width height
```

Все координаты нормализованы в диапазон 0..1 относительно ширины и высоты изображения. Пример:

```text
0 0.512500 0.475000 0.220000 0.310000
```

Правила:

- коробка должна охватывать видимую часть объекта;
- не включайте случайный фон;
- каждый самостоятельный объект размечайте отдельно;
- объект, обрезанный краем кадра, размечайте по видимой части согласно правилам проекта;
- одинаковые объекты не объединяйте в одну коробку;
- пустые кадры имеют пустой label-файл, если инструмент этого требует.

### 6.4. Pose-разметка

Pose-разметка содержит bounding box и набор keypoints. Количество и порядок точек должны быть одинаковыми во всех кадрах. Например:

```yaml
kpt_shape: [4, 3]
```

означает четыре точки, каждая с `x`, `y` и visibility. Координаты keypoints также нормализуются. Порядок следует описать отдельным документом, например:

```text
0: left_top
1: right_top
2: right_bottom
3: left_bottom
```

Не меняйте порядок точек, если уже написан postprocessor. Неверный порядок может давать правдоподобный bbox и полностью неправильный угол захвата.

### 6.5. Контроль разметки

Перед обучением выборочно проверьте не менее 100 изображений:

- наложите боксы и keypoints;
- сравните класс с исходной деталью;
- проверьте изображения без объектов;
- проверьте самые маленькие и частично перекрытые объекты;
- убедитесь, что train, val и test не содержат дублей.

Полезная проверка: отсортировать изображения по размеру объекта и отдельно посмотреть нижние 5% по площади. Именно они часто определяют реальные пропуски.

## 8. Подготовка к обучению YOLO11

### 8.1. Выбор веса

В каталоге `yolo-trainer` есть `yolo11n.pt`, `yolo11s.pt`, `yolo11m.pt`, `yolo11l.pt`, а также pose-веса. Ориентир:

- `n`: быстрый baseline и проверка разметки;
- `s`: хороший первый производственный эксперимент при ограниченной GPU;
- `m`: баланс качества и скорости;
- `l`: больше ресурсов и более медленный inference.

Для `cv-service` важна не только метрика, но и время полного цикла: загрузка кадра, warp, inference, postprocessor и публикация результата. Начните с `s` или `m`, измерьте latency, затем сравните с `l` на той же тестовой выборке.

### 8.2. Исправление текущего trainer.py

Минимальная обязательная правка в `yolo-trainer/trainer.py`:

```python
YOLO_BASE_DETECT_MODEL = 'yolo11m.pt'
YOLO_BASE_POSE_MODEL = 'yolo11m-pose.pt'
```

Остальные параметры текущего скрипта имеют риски:

```python
epochs=2000
batch=0.9999
model.to("cuda")
```

`batch=0.9999` означает автоматический подбор batch в Ultralytics, но результат зависит от видеопамяти. `2000` эпох часто избыточны и увеличивают риск переобучения. Для первого прогона используйте 100-300 эпох, `patience=30-50`, явный `imgsz` и сохранение лучшего checkpoint-а.

Пример самостоятельного запуска через Python:

```powershell
cd yolo-trainer
python -c "from ultralytics import YOLO; m=YOLO('yolo11m.pt'); m.train(data='datasets/312.229.001.v5i.yolov11/data.yaml', epochs=200, imgsz=960, batch=-1, device=0, project='runs', name='312_229_001_yolo11m', patience=40, plots=True)"
```

Для pose замените вес:

```powershell
python -c "from ultralytics import YOLO; m=YOLO('yolo11m-pose.pt'); m.train(data='datasets/312.229.002.v5i.yolov11/data.yaml', epochs=200, imgsz=960, batch=-1, device=0, project='runs', name='312_229_002_pose_yolo11m', patience=40, plots=True)"
```

Для повторяемости сохраняйте команду, версию Ultralytics, имя веса, commit проекта, параметры камеры и hash датасета.

### 8.3. Запуск существующего скрипта

После замены базового веса:

```powershell
cd yolo-trainer
python trainer.py detect 312.229.001.v5i.yolov11.zip
```

или:

```powershell
python trainer.py pose 312.229.002.v5i.yolov11.zip
```

Скрипт:

1. ищет ZIP непосредственно в `yolo-trainer`;
2. распаковывает его в `yolo-trainer/datasets/<имя архива>`;
3. проверяет наличие `data.yaml`;
4. выбирает detect или pose базовый вес;
5. вызывает `train`, затем `val`.

Он не проверяет наличие GPU, не фиксирует версию датасета и не копирует результат в `data/models`. Эти действия выполняются вручную.

## 9. Процесс обучения и мониторинг

### 9.1. Рекомендуемый цикл эксперимента

1. Обучите `yolo11n` или `yolo11s` на небольшой выборке.
2. Проверьте, что loss уменьшается, а картинки из `runs/...` имеют правильные боксы.
3. Исправьте разметку, если визуализация неверна.
4. Запустите основной эксперимент на `yolo11m`.
5. Сравните не менее двух вариантов: размер модели, `imgsz`, augmentation или состав классов.
6. Не выбирайте checkpoint только по одной метрике.

После обучения полезные файлы обычно находятся в `yolo-trainer/runs/<task>/<name>/`:

```text
weights/best.pt
weights/last.pt
results.csv
results.png
confusion_matrix.png
PR_curve.png
F1_curve.png
val_batch*_pred.jpg
```

`best.pt` используйте как кандидата для поставки. `last.pt` нужен для продолжения обучения, а не обязательно для production.

### 9.2. Остановка и переобучение

Признаки переобучения:

- train loss продолжает снижаться, val loss растёт;
- precision на train высока, на test заметно хуже;
- модель уверенно ошибается на новом освещении;
- на контрольных пустых кадрах появляются ложные объекты.

Сначала проверьте разделение данных и разметку. Затем уменьшите число эпох, включите early stopping, добавьте реальные трудные примеры и только потом меняйте архитектуру.

### 9.3. Проверка на независимом тесте

Не используйте test для подбора каждого параметра. Держите его до конца. Отчёт должен содержать:

```text
версия модели:
версия датасета:
число изображений train/val/test:
классы:
precision / recall / mAP50 / mAP50-95:
результат на пустых кадрах:
результат на трудных сериях:
latency одного кадра:
ошибки по типам:
```

Для робота добавьте прикладные показатели: доля циклов с корректным pick point, доля пропусков, доля ложных срабатываний и число опасных решений. Ваша цель не максимальный mAP, а безопасное и повторяемое действие.

## 11. Postprocessor и связь с роботом

YOLO выдаёт геометрию, но производственное решение принимает код postprocessor-а. В проекте файлы лежат в `data/postprocessors` и выбираются из `Models.*.ModelProcessor`.

Перед запуском робота протестируйте postprocessor отдельно на сохранённых предсказаниях:

1. объект без поворота;
2. объект с поворотом на 90 градусов;
3. зеркальная ориентация;
4. частично закрытый объект;
5. два объекта рядом;
6. неправильный класс;
7. пустой кадр.

Проверьте:

- `pick_point` находится внутри допустимой области;
- `pick_angle` находится в ожидаемом диапазоне;
- единицы измерения согласованы с роботом;
- выбор первого объекта соответствует `Process.FirstObjectCriteria`;
- при неоднозначности система отказывает безопасно, а не выбирает случайный объект.

`master-service` следует подключать только после этой проверки. Начните с режима без движения робота: логируйте решения CV, затем используйте эталон и step mode, и только после серии успешных циклов переходите к автоматике.

## 13. Типовые неисправности и диагностика

### Модель не находится

Проверьте, что имя в `ModelFileName` совпадает с файлом в `data/models`, а volume `data:/data` подключён:

```powershell
docker compose exec cv-service ls -l /data/models
```

### CV видит маркеры, но не видит объекты

Проверьте `data/calibration_matrix.npy`, размер warped-кадра, соответствие train-изображений runtime и журнал `cv-service`. Если модель обучалась на исходных кадрах, а runtime подаёт warped-кадр, переобучите на правильном представлении.

### Все confidence низкие

Проверьте класс, масштаб, освещение, порог и соответствие веса задаче detect/pose. Не снижайте порог до нуля до выяснения причины: это может скрыть проблему разметки.

### Неверный pick angle

Проверьте порядок keypoints, `flip_idx`, направление осей после warp и формулы postprocessor-а. Bbox может быть правильным при неправильных keypoints.

### `/api/cv/calibrate` возвращает ошибку

Проверьте, сохранился ли `data/calibration_matrix.npy`. В текущем `Calibrator.py` не определены `Origin` и `Theta`, хотя endpoint пытается вернуть их. Это отдельная проблема API-ответа, а не обязательно провал расчёта матрицы.

### `camera-service` запускается, но кадр не публикуется

Проверьте IP/GigE, MVS Runtime, Redis, наличие `/data/distortion_coeffs.npz` и логи. При отсутствии коэффициентов текущий код может обратиться к неинициализированному `undistorted`; файл для runtime должен быть доступен до запуска.

### Обучение падает на CUDA

Уменьшите `imgsz`, выберите меньшую модель, используйте `batch=-1` или явный меньший batch, проверьте `nvidia-smi`. Если GPU отсутствует, не используйте текущий безусловный `model.to("cuda")`.

## 16. Подбор параметров и сравнение экспериментов

### 16.1. Что менять в первую очередь

Не меняйте одновременно модель, размер изображения, аугментации и состав классов: при таком эксперименте невозможно понять причину улучшения или ухудшения. Практичный порядок такой:

1. Зафиксировать датасет и получить baseline на `yolo11n` или `yolo11s`.
2. Сравнить `yolo11s` и `yolo11m` на одинаковом `data.yaml`, `imgsz` и числе эпох.
3. Проверить два размера входа, например 640 и 960.
4. Только затем исследовать аугментации и баланс классов.
5. Зафиксировать лучшую конфигурацию на независимом test.

Для каждого запуска используйте уникальное имя:

```text
<product>_<task>_<model>_<imgsz>_<dataset-version>
312_229_001_detect_yolo11m_960_ds03
```

Такой формат облегчает поиск `best.pt` и исключает ситуацию, когда файл из старого эксперимента случайно принимается за новый.

### 16.2. Размер входного изображения

Размер `imgsz` должен учитывать минимальный объект. Если объект занимает небольшую часть кадра `4895 x 2960`, слишком маленький вход может потерять признаки дефекта. Но увеличение `imgsz` повышает потребление памяти и latency. Поэтому измеряйте качество и скорость одновременно.

Пример сравнительной серии:

```powershell
python -c "from ultralytics import YOLO; m=YOLO('yolo11s.pt'); m.train(data='datasets/new_product/data.yaml', epochs=150, imgsz=640, batch=-1, device=0, project='runs', name='new_s_640_ds03', patience=30)"
python -c "from ultralytics import YOLO; m=YOLO('yolo11s.pt'); m.train(data='datasets/new_product/data.yaml', epochs=150, imgsz=960, batch=-1, device=0, project='runs', name='new_s_960_ds03', patience=30)"
```

Если `imgsz=960` улучшает recall маленьких объектов, но не укладывается в производственный цикл, рассмотрите уменьшение области интереса до рабочей зоны. Делать это нужно одинаково при сборе данных, обучении и runtime; нельзя просто обрезать кадр только на этапе inference.

### 16.3. Дисбаланс классов

Посчитайте не только число изображений, но и число экземпляров каждого класса. Один класс может присутствовать на каждом кадре, а редкий дефект встретиться пять раз. В этом случае accuracy будет выглядеть хорошо даже при полном провале на дефекте.

Для редкого класса:

- соберите дополнительные реальные сцены;
- добавьте варианты положения и освещения;
- проверьте, что разметчики используют одинаковое определение дефекта;
- не создавайте десятки почти одинаковых копий одного кадра;
- держите часть новых сцен только в test.

Если дефект невозможно физически получить часто, допустима осторожная аугментация, но синтетические примеры должны быть визуально реалистичными и проверяться человеком. Нельзя размножать один и тот же дефект так, чтобы модель запомнила фон, блик или уникальное положение детали.

### 16.4. Порог confidence

Порог из `data/config.json` применяется в `Detector` до postprocessing. Значение `0.9` не является универсально более качественным, чем `0.5`: оно может повысить precision и одновременно пропустить рабочие детали.

Подбирайте threshold по кривой precision-recall и стоимости ошибки. Например:

```text
threshold 0.50: recall 0.995, false positive 4.0%
threshold 0.70: recall 0.982, false positive 1.2%
threshold 0.85: recall 0.931, false positive 0.3%
```

Если ложный захват опасен, threshold может быть высоким, но при этом нужен понятный сценарий «объект не подтверждён». Не превращайте threshold в средство исправления плохой разметки или неверной калибровки.

### 16.5. Augmentation и физический смысл

Условия аугментации должны отражать реальную камеру. Допустимы небольшие изменения яркости, контраста, масштаба и положения, если такие вариации возможны на линии. Вертикальный flip обычно бессмысленен, если деталь физически не может оказаться вверх ногами. Для pose особенно опасны преобразования, меняющие смысл левой и правой точки.

Перед включением сильной аугментации посмотрите несколько сгенерированных изображений. Если человек не может понять, что на них изображено, нейросеть тоже будет учиться на неестественном распределении.

## 17. Аудит датасета перед запуском обучения

### 17.1. Чек-лист структуры

Перед первым запуском создайте отчёт по каждому разделу:

```text
images train / val / test:
labels train / val / test:
пустые изображения:
изображения без label:
label без изображения:
число экземпляров каждого класса:
минимальная и максимальная площадь bbox:
число keypoints на объект:
пустые или повреждённые файлы:
дубли по имени и по содержимому:
```

Пример быстрой проверки наличия пар image/label в PowerShell:

```powershell
$root = 'yolo-trainer\datasets\new_product'
Get-ChildItem "$root\train\images" -File | ForEach-Object {
  $label = Join-Path "$root\train\labels" ($_.BaseName + '.txt')
  if (-not (Test-Path $label)) { "Нет label: $($_.Name)" }
}
```

Скрипт `trainer.py` проверяет только наличие `data.yaml`. Он не проверяет соответствие картинок и labels, корректность диапазона координат или число keypoints. Эти проверки должны быть частью подготовки набора.

### 17.2. Поиск утечки между выборками

Утечка возникает, когда соседние кадры одной серии, один объект или одна фотография после небольшого resize попадают одновременно в train и test. Метрика в таком случае не отражает работу на новой партии.

Разделяйте по группам:

```text
группа A: изделие/серия/условие света -> train
группа B: другая серия -> val
группа C: новая серия и другой день -> test
```

Если один объект фотографировался несколько раз, все его фотографии должны оставаться в одной группе. Для промышленного датасета «новый объект» важнее, чем случайный процент split.

### 17.3. Аудит координат

Для detection допустимы только нормализованные значения от 0 до 1. Проверяйте, что:

- `center_x`, `center_y`, `width`, `height` конечны;
- width и height больше нуля;
- коробка не выходит за границы без осознанного правила;
- class id существует в `names`;
- в каждой pose-строке одинаковое число значений;
- visibility keypoints использует согласованные значения.

Особенно внимательно проверьте экспорт из внешнего инструмента. Некоторые форматы хранят `x_min, y_min, x_max, y_max` в пикселях, а YOLO ожидает центр, ширину и высоту в нормализованном виде. Внешне похожий текстовый файл может быть математически несовместимым.

### 17.4. Контроль визуализацией

Выберите случайно по 20 изображений из каждой комбинации «класс x условие x часть выборки». Наложите labels и просмотрите их в масштабе 100%. Для pose увеличьте точки и проверьте каждую точку по имени, а не только общий силуэт.

Минимальный критерий допуска: другой инженер должен открыть случайный набор и без устных пояснений понять, что именно размечено и почему. Если правила нельзя объяснить на одной странице, сначала уточните ontology классов.

## 18. Интерпретация результатов обучения

### 18.1. Матрица ошибок

Confusion matrix показывает, какие классы модель смешивает. Если `product_ok` часто становится `product_ng`, проверьте границу дефекта и одинаковость правил. Если класс превращается в background, вероятны маленький размер объекта, нехватка примеров или неправильная разметка.

Для нескольких похожих изделий полезно собрать отдельную таблицу ошибок с фотографиями. Число на матрице говорит «сколько», но не говорит «почему».

### 18.2. Precision, recall и mAP

Precision отвечает на вопрос: сколько найденных объектов действительно правильные. Recall: сколько существующих объектов найдено. Для робота false positive на пустой зоне нужно анализировать отдельно, потому что aggregate-метрики могут скрыть редкую опасную ошибку.

`mAP50` обычно мягче, чем `mAP50-95`: высокая первая метрика ещё не означает точную коробку. Для pose отдельно смотрите точность keypoints. Если pick point выводится из keypoints, хороший bbox при плохой геометрии не является успешным результатом.

### 18.3. Ошибки по сценам

Группируйте ошибки по причинам:

```text
плохое освещение
блик
частичное перекрытие
объект у края
неверный класс
неверный keypoint
ошибка калибровки
ошибка postprocessor-а
```

Это важнее одного среднего процента. Если все ошибки происходят у правого края, добавляйте кадры этой зоны и проверяйте маркерную homography, а не просто увеличивайте число эпох.

### 18.4. Когда не надо продолжать обучение

Остановите эксперимент и вернитесь к данным, если:

- на визуализации labels неверны;
- validation быстро достигает 100%, но новый день работает плохо;
- train и val содержат одинаковые серии;
- модель путает класс из-за неоднозначного определения;
- pose-точки имеют разные порядки;
- вход в runtime визуально отличается от train.

Дополнительные эпохи не исправляют систематическую ошибку координат, утечку данных или неверный класс.

## 19. Безопасный выпуск, откат и расследование инцидента

### 19.1. Двухэтапный выпуск

Новый `.pt` сначала устанавливается как отдельная запись модели, например `new_product_v004_candidate`. Старую production-запись не удаляйте. Проверьте candidate на контрольных кадрах, затем на стенде без движения и только потом назначайте её текущей.

Перед переключением сохраните:

```powershell
Copy-Item data\config.json data\config.before_new_product_v004.json
Copy-Item data\models\model_new_product_v003.pt data\models\archive\model_new_product_v003.pt
```

После успешного выпуска не изменяйте содержимое уже выпущенной версии.

### 19.2. Мгновенный откат

Если ухудшились confidence, координаты или latency, верните `Process.LastModel` на предыдущую запись через endpoint выбора модели либо восстановите резервную конфигурацию и перезапустите `cv-service`:

```powershell
curl -X POST "http://localhost/api/cv/change_model?model_name=312.229.001_yolo11m_v003"
docker compose restart cv-service
```

Откат должен быть проверен заранее. Нельзя разрабатывать процедуру отката впервые во время остановки линии.

### 19.3. Карточка инцидента

При ошибке сохраните не только скриншот, но и:

1. исходный кадр из камеры;
2. warped-кадр перед YOLO;
3. обработанный кадр;
4. текущую модель и threshold;
5. calibration matrix и distortion-файл;
6. логи `camera-service` и `cv-service`;
7. состояние `master-service`;
8. номер цикла, изделие и освещение;
9. фактическое действие робота.

Без warped-кадра часто невозможно отличить ошибку модели от ошибки геометрии. Без версии postprocessor-а невозможно воспроизвести pick angle.

### 19.4. Критерии остановки

Автоматический цикл следует остановить и перейти в безопасный режим, если:

- камера потеряла связь;
- отсутствует актуальный кадр;
- не найден ArUco или матрица не соответствует установке;
- несколько кандидатов имеют одинаковую приоритетность;
- pick point выходит за разрешённую область;
- модель или postprocessor не загрузились;
- latency превышает допустимое окно цикла;
- обнаружен новый класс, для которого нет правила робота.

Модель должна иметь путь отказа «не выполнять действие». Это часть приёмки наравне с правильным распознаванием.

## Приложение B. Что улучшить в инфраструктуре обучения

Для регулярной эксплуатации полезно сделать следующие небольшие улучшения:

1. Передавать в `trainer.py` базовый вес, epochs, imgsz, batch, device и имя эксперимента через аргументы.
2. Заменить жёсткие `yolo26` на `yolo11` или добавить явный параметр версии.
3. Проверять `torch.cuda.is_available()` до `model.to("cuda")`.
4. Проверять структуру датасета и соответствие image/label до старта обучения.
5. Сохранять manifest с hash файлов и параметрами эксперимента.
6. Исправить неинициализированный `undistorted` при отсутствии distortion-файла.
7. Исправить ответ `/api/cv/calibrate`, убрав `Origin` и `Theta` либо вычисляя их явно.
8. Добавить smoke-тест загрузки модели, postprocessor-а и одного контрольного кадра.
9. Сделать откат модели одной командой через сохранённую запись `LastModel`.
10. Разделить production, test и экспериментальные каталоги моделей.

Эти изменения не заменяют контрольные испытания, но уменьшают вероятность того, что ошибка в файлах, именах или окружении будет принята за проблему самой нейросети.
